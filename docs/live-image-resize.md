# Live image resizing — plan

**Status: parts 1 and 2 implemented** (backend endpoint, cache, limits, eviction, tests, the Browse
hero banner, and the thumbnail gallery grid). The rest of this document is the original plan; the
gallery's measurements and decisions are recorded under "Part 2 results".

## Goal

Let the UI request a stored image at a specific width and have the backend resize it on demand,
cache the result, and return it — instead of always serving either a pre-generated tier or the
full-resolution file.

Example: a 1080p image is stored once; the UI asks for it at 720 wide; the server resizes, caches
and returns that.

## Non-goals

- **Not replacing the existing tiers.** Library thumbnails keep their pre-generated `small`
  (320 px) and `medium` (800 px) WebP derivatives. Those grid/list/strip paths are hot, and
  generating at write time keeps ffmpeg off the request path. See "Why not replace the tiers".
- **Not touching the base sidecar JPEG, the AI-enhancement original backup, or the stored gallery
  files.** Those stay as they are; live resizing only reads them.
- **No migration**, no column drops, no change to Backfill Images in the first phase.
- **No upscaling.** A request larger than the source returns the source dimensions.

## Current state (what exists today)

Library item images:

| Image | Location | Format | Size | Created |
|---|---|---|---|---|
| Base / sidecar thumbnail | next to the media file under `MediaRoot` (`library.thumbnail`) | JPEG | full resolution | download/import, or any thumbnail replace |
| Small tier | `ImagesRoot/library/<id>/small/<uuid>.webp` (`thumbnail_small_path`) | WebP | ≤ 320 px wide | every time the base is written |
| Medium tier | `ImagesRoot/library/<id>/medium/<uuid>.webp` (`thumbnail_medium_path`) | WebP | ≤ 800 px wide | every time the base is written |
| AI original backup | `ImagesRoot/library/<id>/original/<uuid>.jpg` | JPEG | pre-enhancement base | only the first time AI enhance runs on an item |
| Gallery image | `ImagesRoot/thumbnail-gallery/<id>/<uuid><ext>` | as saved | as saved (video-frame resolution) | "Save in Thumbnail Gallery" / frame picker / Frame Matching |

- Tiers are generated by `imageproc.GenerateTiersFromPath` / `GenerateTiers` (an ffmpeg shell-out;
  the codebase deliberately avoids a cgo image library) at ~12 call sites.
- Filenames are fresh UUIDs on every generation, for browser cache-busting; old derivatives are
  deleted when new ones land.
- Collection covers have small / medium / `original` (1920 px) tiers; artist images have a single
  400 px tier.
- Static serving: `/media-files` (`MediaRoot`) and `/local-images` (`ImagesRoot`), both
  `StaticFS` behind `RequireAuth` with `Cache-Control: no-cache`.
- Frontend helpers `librarySmallThumbnailUrl` / `libraryMediumThumbnailUrl` fall back to the base
  file for items without derivatives.

## Why not replace the tiers

On-demand resizing still needs a cache — a cache of resized files is "tiers, generated lazily".
Replacing the tiers would mean:

- A cold-cache cost: a 50-item library page would spawn up to 50 ffmpeg processes on first view,
  on hardware (NAS / Pi) that the project explicitly targets. Pre-generating at write time pays
  that cost once, off the request path.
- A request-time CPU surface (an authenticated client can make the server do work), needing a width
  whitelist, request coalescing and a concurrency cap.
- A cache eviction/invalidation mechanism (today: "delete old files when new ones land").
- A migration (drop two library columns, collection/artist path columns, the backfill package, the
  "medium derivative tier" setting, DTO/TS fields).

The tier generation is already centralized in one function; the complexity is the plumbing, not
the logic. Disk savings are negligible. So tiers stay; live resizing is an addition for places the
tiers don't fit.

## Candidates

### 1. Browse page hero banner (first rollout)

`frontend/src/components/browse/BrowseHero.tsx:46` loads `mediaFileUrl(item.thumbnail)` — the full
base JPEG — for a 50vh/60vh banner that rotates every 10 s. It is the only library-thumbnail surface
that always loads the original.

- **Why it uses the original:** the medium tier (800 px) looks soft stretched across a
  viewport-width banner.
- **Proposal:** serve the hero as WebP at a width matched to the viewport, chosen by the browser
  via `srcset` / `sizes` (decided). The `<img>` gets a `srcset` listing the whitelisted widths
  (`720w`, `1080w`, `1280w`, `1920w`) and `sizes="100vw"`; the browser picks the smallest candidate
  that covers its layout width × `devicePixelRatio`. No JS width logic. A small helper builds the
  `srcset` string from the whitelist. Smaller than the JPEG at equal visual quality, and bounded
  regardless of how large the source was (a 4K frame today is served at 4K).
- **`srcset` caveats:** the browser's choice is not under our control (it may reuse an
  already-cached larger candidate, and on a window resize it may pick a larger candidate but won't
  swap back down). The `src` attribute keeps the original-file URL as the fallback for
  browsers/situations that ignore `srcset`, and for the error fallback below.
- **Preload (implemented):** the next slide is fetched into the browser cache by a hidden `<img>`
  built from the same attributes as the visible one (`heroImageSource` in `BrowseHero.tsx`), so the
  browser resolves the same `srcset` candidate and reuses the response.
- **Caching:** the base JPEG is overwritten in place on replace, so the response must revalidate
  (ETag / `Last-Modified`), same rationale as the existing `no-cache` on static routes.
- **Fallback:** if the resize endpoint errors, fall back to the existing `mediaFileUrl` so the hero
  never goes blank.

### 2. Thumbnail gallery grid (second rollout, evaluate against the alternative)

`frontend/src/components/library/ThumbnailGalleryDialog.tsx:305` renders every saved image at full
frame resolution in a grid of small tiles (`aspect-video`).

- Findings: the gallery has **no cap** (nothing in `thumbnail_gallery_handler.go` or the repo
  limits count); "Save all to gallery" can add up to 24 frames per click; tiles are plain
  `<img>` with no `loading="lazy"` or `decoding="async"`, so opening the dialog fetches every file.
- **Proposal:** request ~320–480 px wide for tiles. Keep the full file for the fullscreen viewer
  (`ThumbnailGalleryViewerDialog.tsx:136`).
- **Caching:** gallery files are UUID-named and never modified in place, so resized variants are
  immutable → long-lived `Cache-Control: immutable` is safe here.
- **Independent, cheaper improvement (do first):** add `loading="lazy"` and `decoding="async"` to
  the tile `<img>`. This limits *how many* images load; live resizing limits *how big* each is. They
  combine well.
- **Alternative to compare:** generate a small tier at gallery-save time (a write path we already
  own) instead of resizing live. That is the "tier" approach and may be simpler for this surface.
  The point of trying live resizing here is to see if it is good enough in practice.

### Other surfaces that load full-size images (not in scope now, noted for later)

|---|---|---|
| Pick-from-folder dialogs | `ArtistDialog.tsx:282`, `CollectionCoverDialog.tsx:69` | arbitrary user files via `mediaFileUrl(c.relPath)`; unbounded source size; no write path, so live resizing is the only clean fix |

## Design

### Endpoint

```
GET /api/image?root=media|images&path=<relative path>&w=<width>[&h=<max height>]
```

- Behind `RequireAuth` (same as `/media-files` and `/local-images`).
- `root` selects `MediaRoot` or `ImagesRoot`; `path` is resolved with
  `pathsafe.ResolveUnderRoot(root, path)` so traversal is rejected exactly as elsewhere.
- Source must be an image extension the app already handles (`.jpg .jpeg .png .webp`); anything
  else is a `400`.
- Alternative shape: a `?w=` parameter on the existing `/media-files` and `/local-images` routes.
  A dedicated endpoint is clearer and keeps the static routes plain; decide at review time.

### Width whitelist

`w` must be one of a fixed set (proposed: `320, 480, 720, 1080, 1280, 1920`). Anything else is
`400`, never rounded silently. This bounds the number of cache variants and prevents a client from
generating arbitrary sizes. Output width is `min(w, sourceWidth)` — never upscaled; height follows
aspect ratio.

### Optional height cap (`h`)

`h` is optional and means "also cap the height", never "crop to this height" (a Jellyfin-style
`maxHeight`). `w` stays required, so every request still has a bounded, whitelisted width.

- **Semantics:** the image is scaled to fit inside a `w × h` box, preserving aspect ratio, and is
  never upscaled. Equivalent ffmpeg filter:
  `scale='min(iw,W)':'min(ih,H)':force_original_aspect_ratio=decrease`. With `h` omitted this
  reduces to the width-only behavior described above.
- **Why it exists:** a width-only request on a portrait image yields a very tall result (width 1280
  on a 3:4 photo is 1707 px tall). `h` bounds that. Library thumbnails are almost all landscape,
  but the pick-from-folder dialogs show arbitrary user files.
- **Whitelist:** `h` is validated against its own fixed set (proposed: `180, 270, 405, 720, 1080`)
  for the same reason as `w` — it bounds cache variants. Anything else is `400`.
- **Cache key:** includes `h` (a missing `h` is a distinct key from any value).
- **Not included:** no crop, pad or `fit` modes. If a fixed-aspect server-side crop is ever needed
  (e.g. square avatars), that is a separate decision with its own parameter; CSS `object-cover`
  covers every current case.
- **Used by the candidates?** Neither the hero nor the gallery grid needs `h` (both are
  landscape + `object-cover`). It is specified now so the endpoint contract does not change when
  the portrait-prone surfaces (pick-from-folder dialogs) are added.

### Request shape: why width-only

Width-only (aspect ratio preserved) is one of three common shapes for an image-resize API:

| Approach | Example | Used when |
|---|---|---|
| Width only | Next.js image optimizer (`?w=640&q=75`), `srcset` `w` descriptors | Responsive images/thumbnails where the layout decides the final box |
| Width + height with a fit mode | imgproxy, Cloudinary, imgix, Thumbor (`w=300&h=200&fit=cover`) | A fixed box is needed, so the server crops or pads |
| Max width/height bounds | Jellyfin (`maxWidth` / `maxHeight`, plus `quality`) | The server fits the image inside a box without cropping |

Named presets (`size=tile|card|hero`) are a fourth option, common where variants should be tightly
restricted.

**Chosen: width-only**, because:

- Both candidates are fixed-box layouts using `object-cover` (the hero is a fixed-height banner;
  gallery tiles are `aspect-video`). The browser already does the cropping, so the server only
  needs to supply enough pixels across — width is the only variable that matters.
- The existing tiers (320, 800) are width-only, so this keeps one convention.
- No server-side crop means the full frame is preserved and the cached variant stays reusable.

**When this would not be enough:**

- A server-side crop to a fixed aspect ratio (e.g. square avatars from non-square sources).
  Packrat does this in CSS today, so there is no current need.
- Bounding both dimensions, e.g. "fit within 1280×720" for portrait images, where a width-only
  1280 yields a very tall result. Library thumbnails are almost all landscape, but the
  pick-from-folder dialogs show arbitrary user files. If that surface is added later, add an
  optional `h` meaning "cap height too" (a Jellyfin-style `maxHeight`) rather than crop modes; it
  stays compatible with the whitelist. This is part of the design — see "Optional height cap".

**Refinements to consider (not decided):**

- **High-DPI screens:** the caller picks a whitelisted width from `devicePixelRatio`, or uses
  `srcset`/`sizes` so the browser chooses among a few whitelisted widths itself.
- **Named presets over raw widths:** if the whitelist grows beyond a couple of call sites,
  `tile`/`card`/`hero` names avoid scattering magic numbers and let one place retune a size.

### Output

WebP, quality 80 (same as the existing tiers), via the same ffmpeg scale filter
`GenerateWebP` already uses. Reuse that function so the encoding path stays one place.

### Cache

- **Key:** hash of `(root, path, source mtime, source size, w, h)`. mtime+size in the key means an
  in-place overwrite of the source (sidecar thumbnails are overwritten in place) naturally misses
  the cache and regenerates; no explicit invalidation hook is needed.
- **Location (decided):** a new `cache` folder, outside anything `StaticFS` serves — not under
  `ImagesRoot`, which `/local-images` exposes directly. Configured by a new `CACHE_ROOT` env var in
  `config.go`, same pattern as `MEDIA_ROOT` / `IMAGES_ROOT` (default `./data/cache`), so a release
  deployment can point it at any folder the user wants to access directly (e.g. a bind mount).
  In Docker the default sits inside the existing data volume, so no compose change is required.
- **Eviction (decided, v1):** age-based. Stale entries (source mtime changed) are orphaned, not
  removed on their own, so the existing hourly ticker in `main.go` deletes cache files not accessed
  in N days — **default 7 days** (decided; adjustable at any time, so keep it a single named
  constant or setting, not a literal scattered in the sweep). A size cap with LRU eviction is a possible later step if the cache proves large in practice.
- **Write:** to a temp file then atomic rename, so a concurrent reader never sees a partial file.

### Concurrency and abuse limits

- Coalesce identical in-flight requests (one resize per cache key). `golang.org/x/sync/singleflight`
  is not currently a direct dependency (`x/crypto` only); a small keyed-mutex map is the
  alternative.
- Bound concurrent resizes with a semaphore. The repo already has patterns for this
  (`embedMetadataSem` in `library_handler.go`; `transcodeLimiter` in `downloader/ytdlp.go`);
  reuse one rather than inventing a third.
- Per-request timeout (the existing `generateTimeout` is 30 s).

### Response headers

- Library base thumbnails (hero): `Cache-Control: no-cache` + `ETag` (+ `Last-Modified` from the
  source) so the browser revalidates cheaply, consistent with the existing static routes.
- Immutable UUID-named files (gallery): `Cache-Control: private, max-age=31536000, immutable`.
  Decide per-`root`/path convention at review time rather than guessing from the path in the
  handler; an explicit `immutable=1` query flag from the caller is one option.

### Frontend

A single helper alongside `mediaFileUrl` / `imageUrl` in `lib/api.ts`, e.g.
`resizedImageUrl({ root, path, width, height? })`, used only by the candidate call sites. The hero
additionally needs a `srcset` builder (e.g. `resizedImageSrcSet({ root, path, widths })`) that
emits one `url Nw` entry per whitelisted width. No change to the existing small/medium helpers.

## Part 2 results (thumbnail gallery grid)

**Implemented (frontend only, no backend change):** the grid tile `<img>` has `loading="lazy"` +
`decoding="async"` and is served from `/api/image?root=images` with `srcset` 320w/480w/720w and
`sizes` matching the grid (fullscreen dialog, `p-4`, `gap-3`; 2 / 4 / 6 columns below sm / below lg /
lg+, i.e. `(100vw - 32px - (cols-1)*12px) / cols`). 720w is included because a 6-column tile at
1920 css px is ~305 px, which wants ~610 px at DPR 2. `src` stays the original file; a failed
resize drops the srcset (same fallback as the hero). The viewer, "Set as thumbnail", save/remove are
untouched.

**Caching decision:** gallery tiles use the endpoint exactly as it behaves (`no-cache` + ETag /
`Last-Modified`, revalidated with a 304), not `immutable`. Reason: simpler (no new parameter or
backend change) and consistent with every other image in the app.

**Measurements** — item 31 (1920x1080), 30 gallery images (~156 KB JPEG each), Vite dev server
proxying to the dev container, 1034 px-wide viewport (6 columns, 155 px tiles, DPR 1), a fresh
browser origin per row so the browser cache is cold. Totals are from Resource Timing for the
gallery image requests only.

| # | State | Image requests | Body bytes | Notes |
|---|---|---|---|---|
| 1 | Before any change | 30 | 4,669,378 (4.45 MiB) | all 200; first tile done 235 ms, all 721 ms |
| 2 | A only (lazy) | 30 | 4,669,378 | identical: all 30 tiles fit within the viewport + lazy margin |
| 3 | A+B, cold browser + cold server cache | 30 | 185,718 (181 KiB) | all 200, `w=320`; first tile 42 ms, all 386 ms |
| 4 | A+B, reload and reopen (warm browser cache) | 30 | 0 body, ~9,000 transferred | all 30 are 304s (server log: 30 x 304, ~4-85 ms each) |

Server-side, the 30 cold resizes took 7-175 ms each (at most 2 run at once), and the resized files
are a few KB each (30 files = 181 KiB at 320w; 330 KiB at 480w on a DPR 2 / 390 px phone viewport).
Caveat: x86 Docker on a dev machine, not target NAS/Pi hardware; rows 1-3 were single runs.

Lazy loading only matters once the grid overflows the viewport plus the browser's margin (Chromium
loads roughly 1,250-2,500 px ahead). With a 90-image gallery at 390 px wide (2 columns, ~6,000 px
tall), 30 tiles were requested on open and the rest only when scrolled near. Without lazy loading
all 90 (~14 MB of originals) would be fetched on open; with 30 images at desktop widths it is a
no-op.

**Recommendation:** keep live resizing for the gallery. It cuts a 30-frame gallery from 4.5 MB
to ~0.2 MB (about 25x) on first open, the cold-cache cost is small (tens of ms per tile, bounded by
the 2-slot semaphore, 30 tiles in under 0.4 s here), and reopening costs 30 conditional requests of
~300 bytes. A save-time small tier would make the first view marginally faster but needs a new
column/migration, a backfill for existing images and cleanup on delete, for a saving of tens of
milliseconds on a surface opened occasionally. Revisit only if target hardware shows cold-open
latency noticeably worse than here, or if galleries routinely hold hundreds of images where
per-tile 304s add up.

## Rollout

1. **Backend endpoint** + cache + limits + tests (path traversal, whitelist, no-upscale, cache hit,
   mtime invalidation, concurrency coalescing). No UI change.
2. **Hero banner** switches to the endpoint with a fallback to the original URL.
3. **Gallery**: first add `loading="lazy"` / `decoding="async"` (independent of this feature),
   then switch the grid tiles to the endpoint at 320–480 px. Compare against generating a small
   tier at save time; keep whichever is simpler and faster in practice.
4. **Review.** Decide whether the pick-from-folder dialogs and frame-matching review should follow,
   and whether the medium tier can ever be retired. No decision is made now.

Each step is independently shippable and revertable; step 1 alone changes no behavior.

## Risks

- **Cold-cache latency** on first view of a new size (one ffmpeg spawn, ~tens to low hundreds of
  ms typical; not measured on target hardware). Mitigated by the cache and by only using this on
  few-image surfaces.
- **Cache growth** if eviction is not implemented — must ship with step 1, not later.
- **Docker volume layout:** the cache dir must live on a persistent or at least writable path in the
  container; and `docker/data-dev/*` is gitignored but machine-local.
- **CPU contention** with downloads/transcodes on small hosts — the semaphore must be small
  (2 is a reasonable start).
- **Auth surface:** a new authenticated endpoint that does CPU work. No rate limiting exists in the
  app (a deliberate scope cut), so the width whitelist + semaphore are the only guards.

## Open questions

### Decided

1. **Endpoint:** dedicated `/api/image` (not a `?w=` parameter on the static routes).
2. **Cache location:** new `cache` folder, `CACHE_ROOT` env var (default `./data/cache`), so a
   release deployment can point it at a folder the user can reach.
3. **Eviction:** age-based sweep for v1.
4. **Resize method:** ffmpeg via the existing `GenerateWebP` path for now; revisit
   (`golang.org/x/image/draw`) only if process-spawn cost shows up in practice.
5. **Width whitelist:** `320, 480, 720, 1080, 1280, 1920`, unchanged for now.
7. **Height whitelist:** the separate list `180, 270, 405, 720, 1080`, unchanged for now.

6. **Hero width selection:** `srcset` / `sizes="100vw"` over the whitelisted widths — the browser
   picks from layout width × `devicePixelRatio`; no JS width logic.

### Still open

None. All design questions are answered. Small implementation details (exact `sizes` value, helper
naming) are left to implementation time. Eviction age is decided: 7 days.
